# 入群工作区确认与分支策略 开发计划

来源：姜维川反馈（2026-10-13，飞书反馈表「新增 Bot 入群时静默 clone…」「工作区多分支/worktree 开发模式…」）。两条独立提交。

## 一、入群克隆确认

### 现状
有仓库的群，Bot 入群（建群、拉入 Bot）即 `joinWorkspace` → `ensureWorkspace` 发 `workspace.ensure`，daemon 静默托管克隆到 `<home>/workspaces/<群>/<Bot>/<仓库>`。主人想用本机已有目录只能事后在「更改…」改绑。

### 方案
- 新状态 `confirm`（待确认）：分区模式、非共享私聊、**新入群**（`joined: true`）且主人机器在线时，`joinWorkspace` 置 `confirm`，不发 ensure；群里发事件「{bot} · 等待 {owner} 确认工作区：托管克隆或使用本机已有目录」。
- 其余情况沿用现行为：主人离线（上线后自动托管克隆，避免卡死）、强制同步群、共享私聊、更换仓库（`joined: false`）。
- `confirm` 与 `unbound` 同等对待：@ 它本次不执行并提示；机器重连不自动 ensure；群顶部横幅给主人「确认工作区」按钮，打开现有的 `WorkspacePicker`。
- 选择即确认：托管克隆 = `PUT …/workspace {path:null}`（daemon `cd(None)` 走托管克隆）；本机目录 = 现有 cd 流程（`check_cd` 校验 remote）。
- **本机候选扫描**（新协议 `repo.find` → `repo.found`）：daemon 在主目录下有限深度（4 层，跳过隐藏目录与 node_modules/target 等，限量限时）找 origin 与群仓库一致的 git 仓库，同时返回托管克隆的目标路径。服务端 `GET /api/groups/:id/bots/:botId/repo-candidates`（仅主人）。
- 选择器展示：「使用本机已有的仓库目录」列出 `machine_repos` 记录 + 扫描结果（去重）；「托管克隆群仓库」说明克隆的 remote 与目标路径。
- 仓库与工作区页：`confirm` 行显示「待确认」，主人的按钮为「确认…」。

### 测试
- server：入群在线 → `confirm` 且不发 ensure；离线 → 现行为；强制同步群/共享私聊/换仓库不受影响；@ 待确认 Bot 不执行；重连不 ensure；确认（cd null）后 ensure；候选接口转发与权限。
- daemon：`repo.find` 找到匹配 remote 的仓库、跳过不匹配与忽略目录；fixture 往返。
- web：横幅确认入口、选择器展示扫描候选与目标路径、仓库页「待确认」。

## 二、多分支 P1：禁止直推基准分支

### 方案
- 群级开关 `groups.protect_base`（布尔）：**新建群默认开启，已有群保持关闭**（姜维川 2026-10-13 拍板）。群设置「仓库与工作区」tab 中可切换（群管理员）。
- 开启时：
  - `RunStart.workspace` 增加 `protectBase`；daemon 系统提示追加：「不要直接提交/推送到基准分支 {branch}；先 `git switch -c feat/<bot>-<任务>`，提交并推送该分支」。
  - daemon 审批：`git push` 目标为基准分支（显式 `<remote> <branch>`、`HEAD:<branch>`，或当前分支即基准分支时的裸 `git push`）在 workspace 档也必须审批，不可「总是允许」。完全访问档维持现状（不审批）。
- 不做：worktree 隔离（P2）、自动建 MR（P3）。

### 待决问题（不在本期）
- 强制同步模式不同步 `.git`：各副本的分支不互通，「feat 分支 + MR」在强制同步群里只能由持有真实仓库的副本推送；需要在 P2 设计副本与分支的关系后再定。本期开关对强制同步群同样生效（只约束 push 目标），不改变同步逻辑。
- 完全访问档是否也应拦截推基准分支：本期不拦（与现有危险命令底线一致），后续视反馈决定。
