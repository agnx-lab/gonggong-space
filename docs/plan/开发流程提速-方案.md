# 开发流程提速方案（编码 → 测试 → 提交推送）

2026-10-16 在共字君机器（M 系列 10 核 / 16 GB）实测。

## 1. 现状耗时

上一批 3 项需求：最后一个提交 16:43，推送约 17:30，**提交到推送约 45 分钟**，几乎全在等自检。

| 步骤 | 耗时 | 备注 |
|---|---|---|
| typecheck | 8s | |
| lint | 1s | |
| protocol / desktop / tools | 5s | |
| web | 30s | 全量跑时偶发 1~8 个超时，需单独重跑 |
| server | 100~130s | 924 用例，最大头之一 |
| cargo test（无改动） | **654s** | 测试本身只跑约 100s |
| cargo 增量编译（改一个文件） | 36s | 26 个集成测试各自重新链接 |
| cargo 冷编译（新工作区 / 全量重编） | 约 14 分钟 | 观测到一次，原因待查 |

## 2. 根因

1. **macOS 首次启动扫描（最大头）**。每个新链接的测试二进制首次运行要等约 15~20s（`syspolicyd`），第二次运行 0s。cargo 有 28 个测试二进制，每次重编后都要全部重扫：28 × 20s ≈ 9 分钟。
2. **集成测试拆成 26 个二进制**。`crates/gonggong/tests/*.rs` 每个文件都是独立 crate，链接和扫描都要做 26 遍。
3. **机器内存不足**。16 GB 内存，swap 已用 9.1 GB；Chrome、多个 Agent/MCP 进程常驻。server 测试单文件跑 5s，并行全量跑同一文件 34s，node 只用到约 2.7 核。已排除：建库策略（FILE_COPY 只快 5%）、fsync、每用例 DROP DATABASE。
4. **磁盘垃圾**。`target/` 182G（`deps/` 下 55 万个文件），30 个子代理工作区 142G，PostgreSQL 里残留 349 个测试库。
5. **每次都跑全量**。只改 web 也要跑 cargo，本地全量和 Jenkins 全量重复。
6. **偶发失败反复重跑**。web 全量跑时有超时类用例失败，每次都要单独重跑确认。

## 3. 方案

### P0：不改代码，当天生效

| # | 动作 | 预期 |
|---|---|---|
| 1 | 把运行 Bot 的终端或应用加入「系统设置 → 隐私与安全性 → 开发者工具」（先执行 `sudo spctl developer-mode enable-terminal` 让该项出现），免除首次启动扫描 | cargo 654s → 约 110s |
| 2 | 清理：删掉已合并的子代理工作区，`cargo clean` 后重建，删掉残留测试库 | 释放约 300G，`deps/` 不再有几十万文件 |
| 3 | 开发机内存：关掉不用的 Chrome 标签 / App，或把自检放到 高能量君 服务器跑 | server 测试预计回到约 40~60s（待验证） |

### P1：小改动，1 天内

| # | 动作 | 预期 |
|---|---|---|
| 4 | 合并集成测试：`crates/gonggong/tests/*.rs` 改为 `tests/it/main.rs` + `mod xxx;`，只产生 1 个测试二进制 | 增量编译 36s → 约 10s；扫描 28 次 → 3 次 |
| 5 | 按改动范围自检：新增 `scripts/check.sh`，按 `git diff --name-only origin/main` 选择要跑的套件，Jenkins 仍跑全量兜底 | 只改 web 时：约 1 分钟 |
| 6 | 修 web 偶发超时用例（定位全量跑时失败的那几个，改等待方式或放宽单用例超时） | 省掉重跑 |
| 7 | 测试结束自动清理残留测试库：globalSetup 启动时删掉 `gonggong_t_%` / `gonggong_tpl_%` 前缀的旧库 | 不再累积 |

按范围选择套件（方案 5）：

| 改动路径 | 要跑 |
|---|---|
| `packages/protocol/` | 全部 |
| `apps/web/src/ui/`、web 共享代码 | web + desktop |
| `apps/web/` 其他 | web |
| `apps/desktop/` | desktop（含 src-tauri 时加 cargo） |
| `apps/server/` | server |
| `crates/` | cargo |
| 仅 `docs/` | 不跑测试 |

typecheck 和 lint 总是跑（共 9s）。

## 6. 第二轮（2026-10-16 下午）

| 项 | 之前 | 现在 | 做法 |
|---|---|---|---|
| server 测试 | 100~130s | 60~84s（连跑 4 次全绿） | 每个测试文件复用数据库，用例间 DELETE 清表（关外键触发器）+ 重置序列，不再每个用例建库删库；种子用户的密码哈希按密码缓存；登录的诱饵哈希改为每个进程算一次 |
| cargo 测试 | 45~72s | 22~32s | `tls` 拆回独立二进制：它用暂停时钟测全局 HTTP 客户端的超时，合并后与其他测试共用客户端会卡死 |
| 全量 `pnpm check --all` | 362s | 125s | |

实测后放弃的：
- 自检并行：cargo 与前端并行只快 19s（132s → 113s），三路并行反而 149s（内存 16G、swap 9G），不值得增加脚本复杂度。
- 清表用 TRUNCATE：比 DELETE 慢（全量 86s 对 73s），它要为每张表重建文件。

提速后暴露的测试竞态（都是后台引擎与用例本身并发，已修测试）：
- `groups` / `runs` 的「查询次数」断言会把后台引擎的查询算进去：改为测 3 次取最小值。
- `workspaces` 的绑定目录用例：daemon 上线后的补发可能先发一条 ensure，改为跳过无关消息只等 cd。产品侧遗留：daemon 重连与建群同时发生时，补发可能在 bot 进入 `confirm` 前多发一次 clone，影响小，未改。

注意：清表用 `session_replication_role`，需要超级用户。本地与 GitHub CI 的 PostgreSQL 都是超级用户；Jenkins 若不是，会直接报权限错误。
